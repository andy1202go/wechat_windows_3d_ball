# 物理在逻辑平面上求解，三维位置由渲染推导

Status: accepted

物理真值完全放在一个平坦的二维**逻辑平面**上：球心坐标、速度、所有碰撞只在这个平面里计算；three.js 场景中的三维位置由该二维坐标加上此处的台面高度推导出来，物理层不感知三维几何，也不知道 three.js 的存在。

原版 3D Pinball 的引擎标注就是「3D，实属 2D」，我们沿用同一模型：立体感是渲染的产物，不是物理的前提。收益是碰撞问题退化成「圆 vs 线段/圆弧」这类闭式求解——不需要连续碰撞检测，不需要求解器迭代，球速再高也不会穿透薄壁。代价是球没有真正的三维自由度，不能飞出坡道；原版也没有，所以这在复刻语境下不构成损失。

## Considered Options

- **三维球体 + 挤出几何碰撞**：能做真正的飞球，但穿透、接触抖动、能量守恒三个问题都要自行解决，而收益只是「比原版更自由」。
- **引入通用刚体引擎**：见 [0003](./0003-custom-2d-physics.md)。

## Consequences

- 台面所有碰撞体必须能表示为平面上线段、圆弧、圆的集合。原版的坡道与斜槽本质上是「另一个二维拓扑」，需要时按**台面层**切分，而不是靠三维几何表达。MVP 只做单层。
- 渲染几何与碰撞几何从同一份二维路径数据生成，二者不可能不一致——这消除了弹球游戏最常见的一类 bug。
- 物理与渲染必须解耦成两个可独立运行的模块：物理要能在没有渲染的情况下跑（调试图、单元测试），渲染要能在没有物理的情况下跑（静态台面预览）。
