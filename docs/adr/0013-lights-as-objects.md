# 灯是独立对象，按灯组管理

Status: accepted

原版画面里灯是主体，不是点缀。资源清单里 `lite1`…`lite322` 共 300 余个灯的图形，另有 20 多个逻辑灯组：`middle_circle`、`outer_circle`、`fuel_bargraph`、`worm_hole_lights`、`hyperspace_lights`、`skill_shot_lights`、`l_trek_lights` / `r_trek_lights`、`bsink_arrow_lights`、`top_target_lights`、`bumper_target_lights`、`bmpr_inc_lights` 等等。灯组用 `Shorts` 字段引用灯的 id 列表——灯在数据模型里是一等公民。

而我们的台面贴图上**一盏灯都没有**。更要紧的是，原版靠灯表达状态：使命进度（蓝圈逐格点亮）、军衔（橙圈）、燃料余量（6 格递减条）、当前可打的目标（目标指示灯）。这些状态全靠「某几盏灯亮/灭」呈现。

所以灯做成**独立对象**，而不是画进贴图的静态装饰：每盏灯有自己的位置与状态，按原版灯组分组管理——一组灯可以整体点亮、熄灭、闪烁。

代价是绘制开销，处理方式是**合并绘制**：所有灯共用一份顶点缓冲，按灯组批量更新，而不是每盏灯一个 draw call。300 个独立 Mesh 在小游戏上不可接受，合并后仍在个位数。

## Consequences

- 贴图只画静态部分（底色、图案、文字标识、装饰线条），动态部分全部交给灯对象。两者边界要清晰——**画进贴图的灯就再也改不了状态了**。
- 灯的位置来自原版灯组数据，与台面元素共享同一套坐标映射（ADR-0011）。
- 「视觉 + 碰撞体、不写行为」这条约束（ADR-0012）对灯不适用：灯没有碰撞，它是纯视觉。点亮逻辑属于视觉表现，不属于玩法行为——**使命系统本身仍在范围外，但灯要能亮**。
- 中央灯环（中圈 9 + 外圈 19）与燃料条（6 格）是第一批要落地的灯组：它们既是画面的视觉焦点，也是原版反馈界面最直观的两处。
- 灯的「亮/灭」不能只靠改材质颜色实现——原版的灯是**图形**（点亮的灯有独立的位图，带光晕与色相变化）。程序化路线下这意味着每盏灯至少要画两种形态（灭/亮），并且要能在合并绘制的前提下切换。M3 需要先定出这条管线的样子再动手铺灯。
