# 载体选小游戏，不选小程序

Status: accepted

我们原计划做成「微信小程序」，但微信《小程序类目不符行为》5.7.5 明确把「不依托其他场景的纯游戏形态」列为违规，处理梯度是警告 7 天 → 下架 → 封号，官方给出的出路是「重新注册小游戏开展」。所以载体定为**微信小游戏**。

这不是一个可以后面再改的技术决定：小游戏账号与普通小程序账号是两套独立账号，AppID 独立，注册时选定的账号类型**不可逆**，选错只能换邮箱重新注册。因此必须在写第一行代码前定下来——包括所有看似与载体无关的目录结构（小游戏没有 `app.json`/WXML，入口是 `game.js`）。

## Considered Options

- **微信小程序**：零资质成本、开发工具链最顺，但必然过不了审，只能停留在开发者工具里。适合纯练手，不适合"做出来给人玩"。
- **先做小程序原型、验证后再迁小游戏**：引擎层（物理、投影、渲染、玩法）可以 100% 复用，返工集中在页面外壳与资源加载。代价是要维护两套外壳。
- **微信小游戏**（选定）：唯一合规路径。

## Consequences

- 需要游戏软著 + 工信部备案 + 防沉迷与适龄提示接入，审核标准比普通小程序严苛得多。
- 个人主体只能申请休闲等有限二级类目（棋牌、角色类不对个人开放），且**不支持虚拟支付**，只能走广告变现。
- 包体按小游戏规则算：主包 ≤ 4M，主包加分包合计 ≤ 30M。这直接约束了 three.js 的引入方式。
- 没有 WXML/WXSS，UI（计分板、暂停、结算）必须用 canvas 或 WebGL 自绘。
